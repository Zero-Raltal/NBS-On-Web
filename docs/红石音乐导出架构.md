## 0. 一句话总览

NBS 的导出流程是**两段式**，不要把这两段混在一起看：

```
           ┌──────────────────────────────────────────┐
           │ 第一段：几何（GML 原版拥有，不要重写）      │
           │ S.grid（音符网格）                        │
           │      ↓  schematicExport()                 │
           │ SCH_BLOCK / SCH_DATA（方块 ID + data 缓冲）│
           │      ↓ noteblocks[]（音符盒位置与音高）     │
           └──────────────────────────────────────────┘
                              ↓
           ┌──────────────────────────────────────────┐
           │ 第二段：容器（每种格式各不相同）            │
           │ M1  legacy .schematic  (gzip NBT, 1.11-)  │
           │ M2  结构方块 .nbt       (gzip NBT, 1.13+) │
           │ M3  .mcstructure        (小端 NBT, 基岩)   │
           │ M4  .mcworld            (ZIP+LevelDB,基岩) │
           └──────────────────────────────────────────┘
```

**核心约束（用户明确要求，违反会被打回）**：
红石布线几何 **只能来自 NBS 自己的 `schematicExport()`**。基岩版导出只借 cbnote 的**容器规则**（`.mcstructure` 的 NBT 布局、`.mcworld` 的 ZIP/LevelDB 打包），**绝不移植 cbnote 的 `buildRedstoneLayout`**。NBS 的三种布局（环形过道 0 / 普通过道 1 / 经典 2）始终由 `schematicExport` 自己算。

## 1. 第一段：几何是怎么算出来的

### 1.1 唯一的入口

```js
// nbsweb/js/schematic.js:578
function schematicExport() { ... }
```

它做三件事，顺序不能变：

1. `ensureSchematicState()` —— 补齐 `S.sch_exp_*` 一堆字段的默认值（首次调用时 `resetSchematicExport(false)`）。
2. 按 `S.sch_exp_layout` 分支铺方块，全部写进两个全局 `Map`。
3. `return schematicWriteNbt({...})` —— 把缓冲序列化成选定格式的字节。

### 1.2 方块缓冲区：`SCH_BLOCK` / `SCH_DATA`

```js
// schematic.js:28-35
const SCH_D = 32000;                              // = sqrt(2000*256*2000)，GML 的二维数组分块宽
function schT(x, y, z) { return x * 2000 * 256 + z * 2000 + y; }   // 线性地址
function schBlockWrite(x, y, z, val) { SCH_BLOCK.set(schT(x, y, z), val); }
function schBlockRead(x, y, z)  { return SCH_BLOCK.get(schT(x, y, z)) ?? 0; }   // 缺省 = 0 = 空气
function schDataWrite(x, y, z, val) { SCH_DATA.set(schT(x, y, z), val); }
function schDataRead(x, y, z)  { return SCH_DATA.get(schT(x, y, z)) ?? 0; }
```

**坐标约定（最容易搞错的地方，务必背下来）**：

| NBS 缓冲轴 | 含义 | 上限 | 换算到 Minecraft |
|---|---|---|---|
| `a`（第 1 参） | **长度 / 时间** | `len` = `schematicLength()` | → `Z` |
| `b`（第 2 参） | **宽度 / 音高** | `wid` = `schematicWidth()` | → `X`，**且要镜像：`X = wid-1-b`** |
| `c`（第 3 参） | **高度 / 层** | `hei` = `schematicHeight()` | → `Y` |

> **镜像的唯一权威出处**：`schematicWriteNbt()` 里写音符盒方块实体时用的是
> `x = wid - 1 - noteblocks.y[a]`（`schematic.js:1161`），紧接着 `y = noteblocks.z[a]`、`z = noteblocks.x[a]`。
> 也就是说 `(NBS a,b,c) → (MC X,Y,Z) = (wid-1-b, c, a)`。
>
> **注意**：这只是「NBS 宽度轴与 Minecraft X 轴的坐标约定差」，**不是世界镜像**。
> 曾经有 Agent 误以为世界被镜像，于是把火把的 east/west 也对调了一次，结果火把全部贴到红石线上掉落。别重犯。

### 1.3 三个辅助写块函数

```js
function blockWalkway(x, y, z)   // 写"过道方块"（S.sch_exp_walkway_block/data）
function blockCircuit(x, y, z)   // 写"电路底板"（S.sch_exp_circuit_block/data）
function blockOther(x, y, z, id, data)          // 写任意方块
function blockRepeater(x, y, z, delay, dir, powered)
//   → id = 93 + powered（93 未激活 / 94 已激活）
//   → data = delay*4 + dir     （低 2 位是方向，高 2 位是延迟 0..3）
```

`blockRepeater` 的 `data` 编码是**全局最关键的一条**，基岩版导出要靠它拆出方向和延迟。

### 1.4 尺寸计算（导出前必须先跑）

```js
calculateSize()        // 算 S.sch_exp_repeaters / S.sch_exp_maxheight / S.schExpEnda
schematicLength()      // 依赖上面两个量
schematicWidth()
schematicHeight()      // = 4 + 3*ceil(maxheight[compress] / 4)
```

**陷阱**：`schematicLength()` 依赖 `S.sch_exp_repeaters` / `S.sch_exp_maxheight`，这两个量**只在 `calculateSize()` 里算**。不先调它 → `repeaters` 全 0 → `len` 只算出 6 → 经典布局一个音符盒都放不下 → **导出一个空壳，而且不报错**。
任何"借用布局"的代码路径都必须先 `ensureSchematicState()` + `calculateSize()`。

另一个陷阱：`calculateSize()` 里有一段 `if (!S.sch_exp_tempo_ready) { ... S.sch_exp_tempo = ... }`，它只在**打开窗口那一刻**按 `S.tempo` 推一次，之后不能再覆盖，否则用户在窗口里选的"5 红石刻/秒"会在下一帧被冲掉。要按当前速度重算就必须临时复位这个标记。

### 1.5 音符盒数据从哪来

`schematicExport()` 里 `noteblocks` 是**局部变量**，`schematicWriteNbt()` 也不返回它。为了给基岩版导出用，加了一个可选钩子：

```js
// schematic.js:1083 —— 在 return 之前
if (typeof S.schExpNoteSink === 'function') {
  try { S.schExpNoteSink(noteblocks, { len, wid, hei }); } catch (_) { }
}
```

- `noteblocks` 形状：`{ n, x[], y[], z[], note[], ins[], pit[] }`，`x/y/z` 是 **NBS 坐标**（未镜像），`note = key - 33`（0..24）。
- 不设这个回调时行为完全不变，既有调用方（数据包 / schematic 导出）零影响。
- **这是给基岩版用的主要数据源，不要改成返回值**，会破坏其它调用方。

## 2. 第二段：四种容器格式

### 2.1 格式对照表

| 代号 | 产物 | 适用版本 | 序列化 | 入口函数 | 压缩 |
|---|---|---|---|---|---|
| M1 | `*.schematic` | ≤ 1.11 | **大端** NBT | `schematicWriteNbt()` 的非 structure 分支 | gzip(stored) |
| M2 | `*.nbt`（结构方块） | 1.13+ | **大端** NBT | `schematicWriteNbt()` 的 structure 分支 | gzip(stored) |
| M3 | `*.mcstructure` | 基岩版 | **小端** NBT | `bedrockExportStructure()` | 无 |
| M4 | `*.mcworld` | 基岩版 | ZIP(STORE) + LevelDB | `bedrockExportWorld()` | 无 |

### 2.2 M1 / M2 的 NBT writer

```js
// schematic.js:400 —— 继承 nbs.js 的 ByteWriter（小端），只补大端方法
class NbtWriter extends ByteWriter {
  be16 / be32 / beFloat / beDouble / beStr     // 大端基础类型
  tagCompound(name)  { push(10); beStr(name); }
  tagEnd()           { push(0); }
  tagByte / tagShort / tagInt / tagFloat / tagDouble / tagString
  tagList(name, len, type)        // ⚠ 参数顺序是 (名字, 长度, 元素类型)
  tagByteArray(name, len)
}
```

> `tagList` 的参数顺序是 `(name, len, type)`，**和 GML 的 `TAG_List(name, len, type)` 一致**，但和某些 NBT 库的 `(name, type, len)` 相反。写的时候容易搞反。

### 2.3 M1：legacy `.schematic`

结构（`schematic.js:1101-1205`）：

```
Schematic(compound)
├─ Height, Length, Width        (short)  ← 注意顺序：Height 在前
├─ Entities(list of 10)         矿车（可选）
├─ TileEntities(list of 10)     告示牌 + 全部音符盒 + 箱子
│   每个音符盒：{ id, x, y, z, note(byte) }
│   ⚠ id 两套：old ? 'Music' : 'minecraft:noteblock'
│   ⚠ x = wid - 1 - noteblocks.y[a]   ← 镜像在这里
├─ Materials = "Alpha"
├─ Blocks(byte[]) 索引顺序：for c → for a → for b = wid-1 downto 0
├─ Data(byte[])   同顺序
└─ Version(compound)  old ? {Name:"1.8", Snapshot:0} : {Id:922, Name:"1.11.2", Snapshot:0}
```

**`Blocks`/`Data` 的遍历顺序必须逐字照抄**：`c` 外层、`a` 中层、`b` 从 `wid-1` 递减。这是 Minecraft 读取 `.schematic` 时的既定顺序，改一个字母整个文件就错位。

### 2.4 M2：结构方块 `.nbt`（1.13+）

结构（`schematic.js:1206-1433`）：

```
(compound, 无名)
├─ DataVersion = 1519                    （对应 MC 1.13.x）
├─ size(list of 3, type 3)  = [32, hei, min(len,32)]
├─ palette(list of 10)
│    [0] walkway  [1] circuit  [2] ground
│    [3 .. 3+insnum-1]  每个音色的底座方块（insnum=10 时补 axis=y）
│    接着每个音色 25 个音符盒状态：{Name:'minecraft:note_block',
│                                  Properties:{instrument, note, powered:false}}
│        或（S.command_block=true）{Name:'minecraft:command_block',
│                                   Properties:{facing:'up'}}
│    再往后是固定段：blue_wool / air / ladder / redstone_wire /
│                    repeater(delay 1..4 facing east) /
│                    repeater(delay 1..4 facing west) /
│                    repeater(delay 4 facing south powered true) /
│                    redstone_torch(lit false/true) /
│                    stone_button / oak_wall_sign / powered_rail /
│                    chest / rail / redstone_wall_torch×4 / lever /
│                    redstone_wall_torch(north)
├─ entities(list of 10)                  矿车
└─ blocks(list of 10)
     ├─ 第一条：出口告示牌（nbt + pos + state=insnum*26+19）
     │   ⚠ nbt 用 1.13 旧式 `Color` + `Text1`~`Text4`（JSON 字符串），
     │     配套 DataVersion=1519，由 DataFixerUpper 升级到新版。这是刻意为之。
     │     详见 §3B「告示牌文字：两种策略」——那里也记录了 cbnote 的不同做法。
     ├─ 可选：循环告示牌（state=insnum*26+19）
     ├─ 全部音符盒（state = 3 + insnum + (ins*25 + note)）
     │   ⚠ S.command_block=true 时 state 退化为 3+insnum，并带 playsound 的 nbt
     ├─ 可选：箱子（state=insnum*26+21）
     └─ 其余方块：for c → for a → for b = wid-1 downto 0
           state 用一长串 if 映射（见 schematic.js:1393-1426）
```

**palette 索引的算术关系**（改动时必须同步）：

```
0                       walkway
1                       circuit
2                       ground
3 + i                   (i = 0..insnum-1) 第 i 个音色的底座
3 + insnum + k          (k = 0..insnum*25-1) 音符盒状态
insnum*26 + 3           blue_wool                ┐
insnum*26 + 4           air                      │
insnum*26 + 5           ladder                   │
insnum*26 + 6           redstone_wire            │
insnum*26 + 7..10       repeater delay1..4 east  │
insnum*26 + 11..14      repeater delay1..4 west  │
insnum*26 + 15          repeater delay4 south powered
insnum*26 + 16          torch lit=false          │
insnum*26 + 17          torch lit=true           │
insnum*26 + 18          stone_button             │
insnum*26 + 19          wall_sign                │
insnum*26 + 20          powered_rail             │ 固定 26 项
insnum*26 + 21          chest                    │
insnum*26 + 22          rail                     │
insnum*26 + 23          wall_torch lit=f east     │
insnum*26 + 24          wall_torch lit=t east     │
insnum*26 + 25          wall_torch lit=f west     │
insnum*26 + 26          wall_torch lit=t west     │
insnum*26 + 27          lever                    │

└
palette 总长度 = 29 + insnum*26  ← 与 GML schematic_export.gml:727 一致
```

> 注意 `state` 的映射里 **没有 `insnum*26+0/1/2`**（那三项是 walkway/circuit/ground，走前面的 `if`）。跳号不是 bug，是重排后的结果。

### 2.5 M3：基岩版 `.mcstructure`（`nbsweb/js/bedrock.js`）

**关键区别：基岩版 NBT 是小端（little-endian）**，所以 `bedrock.js` 有自己独立的 writer：

```js
class BeNbtWriter { u8 / u16 / i32 / i64 / f32 / f64 / str / tag / val }
function beNbtSerialize(rootTags) → Uint8Array
```

根结构：

```
(compound, 无名)
├─ format_version = 1
├─ size(list of 3, type 3) = [sx, sy, sz]
├─ structure(compound)
│   ├─ block_indices(list of 9) = [ 索引数组(int list), 全 -1 数组(int list) ]
│   ├─ entities(list of 10, 空)
│   └─ palette(compound)
│       └─ default(compound)
│           ├─ block_palette(list of 10)   每项 {name(str), states(compound), version(int)}
│           └─ block_position_data(compound)   键 = 扁平索引字符串 → {block_entity_data}
└─ structure_world_origin(list of 3, type 3) = [0,0,0]
```

**扁平索引** = `x*(sy*sz) + y*sz + z`。
**palette[0] 必须是 `minecraft:air`**（基岩版约定）。

方块翻译器：`bedrockBlockFromId(id, data)` → `{ name, states[{name,type,value}] }`。这是整个基岩版导出**唯一需要判断方向语义**的地方，见第 4 节。

### 2.6 M4：基岩版 `.mcworld`

`.mcworld` 就是一个 **ZIP（STORE，不压缩）**，里面有：

| 文件 | 内容 |
|---|---|
| `level.dat` | 8 字节头 `u32LE 10` + `u32LE nbtLen`，后接小端 NBT（`bedrockBuildLevelDat()`） |
| `db/000005.ldb` | LevelDB SSTable（`bedrockBuildSSTable()`） |
| `db/CURRENT` | 字符串 `MANIFEST-000004\n` |
| `db/MANIFEST-000004` | `bedrockBuildManifest()` |
| `levelname.txt` | 世界名 |
| `world_behavior_packs.json` / `world_resource_packs.json` | 空数组 `[]` |
| `world_icon.jpeg` | 预览图（`bedrockWorldIcon()`，canvas 800×450） |

**LevelDB SSTable 的关键细节**（手写很容易错）：

- 内部键 = 用户键 + 8 字节尾，**只有首字节是 `0x01`**，其余 7 字节为 0。
- 块按 `BLOCK_TARGET = 4096` 分组，每条 entry 估算大小 = `15 + ikLen + valueLen`。
- 块内每条 entry：`varint(shared=0)` + `varint(keyLen)` + `varint(valLen)` + key + val。
- 块尾：restart offsets（u32 LE 数组）+ `u32 LE` restart 数量。
- 块 trailer：`0x00` + **masked CRC32C**（u32 LE）。
- footer：`varint(metaIdxOff)` + `varint(metaIdxSize)` + `varint(idxOff)` + `varint(idxSize)`，补零到 **40 字节**，接魔数 `0x57 0xfb 0x80 0x8b 0x24 0x75 0x47 0xdb`。
- Log record（MANIFEST 用）：4B masked CRC32C（覆盖 typeByte+data）+ 2B 长度 + 1B 类型 + data。

**区块键**：`u32 LE cx` + `u32 LE cz` + `u8 tag` [+ `u8 subY`]。

| tag | 含义 | 值 |
|---|---|---|
| `0x2b` | Version | 540 字节（270 对 `0x04`） |
| `0x2c` | — | `[0x2a]` |
| `0x2f` | SubChunk | 每个 subY 一条 |
| `0x31` | BlockEntity | 拼接的 NBT compound |
| `0x36` | — | `[2,0,0,0]` |
| `0x3f` | — | `[0xb5,0x60,0x75,0xfd,0x69,0x2a,0x3c,0x93]` |
| `0x40` | — | `[0x00,0x0a]` |
| `0x41` | — | `[0x00]` |
| `0x77` | — | 空 |

**SubChunk v9** 格式：`[9, 1, subY&0xFF, (BITS<<1)|0, ...索引字节, pc(u32 LE), ...调色板项]`
- `BITS`：`pc<=4 → 2`，`<=16 → 4`，`<=256 → 8`
- 格内索引 = `x*256 + z*16 + y`，位按 **LSB-first** 打包
- `BEDROCK_WORLD_BASE_Y = -60`（世界基准 Y）

## 3. 音符盒音高/音色的三条铁律

这是"导出的地图能不能正常响"的核心，比方向更容易错。

### 3.1 音高在方块实体里（基岩版）

基岩版音符盒的 pitch **不在方块状态里**，而在方块实体：

```
{ id: 'Music', note: 0..24, x, y, z }
```

`note = gKey - 33`。漏了这条 → 所有音符同音高。

Java 版（M1/M2）则在 `TileEntities` / `palette` 里，见 2.3 / 2.4。

### 3.2 音色由音符盒**正下方**的方块决定

`blockOther(xx-1, y1+dir*2, b*3+1, 25, 0)` 写音符盒（id 25），紧接着
`blockOther(xx-1, y1+dir*2, b*3, ins_block, ins_data)` 写它**正下方**的底座方块。

14 种乐器底座由 `S.sch_exp_ins_block[]` 决定，默认值（`resetSchematicExport`）：

```js
[3, 5, 4, 12, 20, 35, 82, 41, 174, 216, 42, 88, 86, 133, 170, 89]
// dirt, planks, cobble, sand, glass, wool, clay, gold, packed_ice,
// bone, iron, soul_sand, pumpkin, emerald, hay, glowstone
```

所以：**音符盒与它下方的底座必须落在相邻格，且镜像换算要对同一个 `wid-1-b`**，否则音色全错。

### 3.3 基岩版没有 `powered` 属性

中继器是两个**不同 ID**：`minecraft:unpowered_repeater` / `minecraft:powered_repeater`。
NBS 的 `93 + powered` 正好对应，无需额外状态。

## 3B. 告示牌文字：两种策略（旧格式靠 DFU 升级 / 新格式直写）

> **不是 bug，是两种不同的兼容策略。** 本节把两边各自的选择、依据、以及
> 改动时的注意事项记录清楚，供 cbnote 侧参考。
>
> **nbsweb 侧无需修改**：它声明 `DataVersion=1519`，`Text1`~`Text4` 由
> DataFixerUpper 正常升级。**cbnote 侧也无需修改**：它声明 `DataVersion=4325`
> 并直写 `front_text`/`back_text`，在其目标版本下是正确写法。

### 3B.1 两边的实测产物

同一件事（在 Java 结构方块 `.nbt` 里给告示牌写文字），两边写法不同：

| 维度 | nbsweb | cbnote |
|---|---|---|
| 文件 | `schematic.js` `schematicWriteNbt()` | `cbnote-v9.html` `rsJavaBlockNbt()` (4383) |
| **DataVersion** | **1519**（MC 1.13.2） | **4325**（MC 1.20.4） |
| **文字格式** | **1.13 旧式**：`Text1`~`Text4` | **1.20 新式**：`front_text` / `back_text` |
| 每行内容 | JSON **字符串**：`'{"text": "Song generated"}'` | 文本组件 **Compound**：`{text:"...", color:"...", bold:1}` |
| 附加字段 | `Color: "black"` | `color`（在 front_text 内）、`has_glowing_text`、`is_waxed` |
| 文字来源 | **硬编码** 4 行版权字样 | `getRedstoneSignText()` 动态生成，含作者/日期/时间 |
| 告示牌方块 | `oak_wall_sign`（墙牌） | `oak_sign`（站立牌） |
| 方向状态 | `facing: "south"` | `rotation: "4"` |

**nbsweb 实测产物**（`DataVersion=1519`）：

```json

**cbnote 实测产物**（`e2e-redstone.nbt`，`DataVersion=4325`）：

 "back_text":{"has_glowing_text":0,"color":"black",
   "messages":{"items":[{"text":""},{"text":""},{"text":""},{"text":""}]}},
 "is_waxed":1}
```

### 3B.2 策略 A（nbsweb）：声明低版本，靠 DataFixerUpper 向前升级

nbsweb 是 GML 原版的忠实移植，而 GML 只支持到 1.13：

```js
// schematic.js —— DataVersion 与 Text1..Text4 一起声明 1.13 语境
w.tagInt('DataVersion', 1519);
w.tagString('Text1', '{"text": "Song generated"}');
```

**机制：`DataVersion` 是"这份数据是哪个版本写的"的声明。** 当声明的版本
**低于**运行中的游戏版本时，Minecraft 的 DataFixerUpper 会按
1.13 → … → 当前版本逐级跑修复规则，`Text1`~`Text4` 会被自动迁移进
`front_text.messages`。所以旧格式 + 旧 DataVersion 是**自洽的一对**，
在 1.20+ 里也能正确显示。

这是"一次写入，向上兼容所有新版本"的策略。

> ⚠ 不能只改其中一半：`DataVersion=1519` 同时还决定了 `palette` 里
> `note_block` 用 `Properties{instrument,note,powered}` 这个 1.13 写法。
> 想换文字格式就必须整体重新对齐到新版本，不能只动告示牌那一处。

### 3B.3 策略 B（cbnote）：声明高版本，直写新格式

cbnote 声明 `DataVersion=4325`（1.20.4），并直接写 1.20 的
`front_text` / `back_text` 结构。

这是"面向当前版本直写，避免依赖修复链"的策略。cbnote 设计上要让
告示牌文字能覆盖 1.13 到最新版本的显示需求（避免 1.20.x 以下读不出牌子），
因此选择了新模式作为主格式。

**两种策略的取舍：**

| | 策略 A（nbsweb） | 策略 B（cbnote） |
|---|---|---|
| 数据声明版本 | 1.13（1519） | 1.20.4（4325） |
| 依赖 DFU 升级链 | **是**（核心机制） | 否（本版本内直接可读） |
| 在 1.20+ 显示 | 正常（经升级） | 正常（原生） |
| 在 1.13 显示 | 正常（原生） | 取决于游戏对未知字段的容忍度 |
| 富文本样式 | 需靠 DFU 解析 JSON 字符串 | 结构化 Compound，表达力完整 |

> **需要注意的一点（供 cbnote 侧判断，非缺陷）**：`DataVersion=4325` 高于
> 1.13~1.19.x。DataFixerUpper 只做**向前**升级、没有降级路径；当一份数据的
> 声明版本高于游戏本身时，游戏不会把它当作旧数据来修复。
> 因此若"1.20.x 以下也要正确读出告示牌"是硬需求，仅靠新格式字段可能不足，
> 需要按目标版本分支写不同字段（或在低版本场景输出策略 A 的字段）。
> 这一判断取决于 cbnote 的实际支持矩阵，本节只记录事实，不预设结论。

### 3B.4 修改时必须守住的不变量：`messages` 不能混类型

无论选哪种策略，只要写 `front_text.messages`，就必须遵守一条 NBT 规则：

**`messages` 是 `TAG_List`，NBT 规范要求同一 List 内所有元素类型一致。**

[Minecraft Wiki · Sign/BE](https://minecraft.wiki/w/Sign/BE) 记 `messages` 为
"a list of text for each line"；1.20 起文本组件既可以是 `TAG_String`（纯文本行），
也可以是 `TAG_Compound`（带样式行）。Mojang 自己在
[MC-279252](https://bugs-legacy.mojang.com/browse/MC-279252) 里说明了这个后果：

> *"Due to text components being changed from strings containing JSON to NBT structures,
> the messages lists in signs can be either a list of 4 strings or a list of 4 compounds.
> If all lines are unformatted, they resolve to strings. A side-effect…"*

即：**同一块牌子的 4 行必须"同为 String"或"同为 Compound"，不能混。**

cbnote 现状（`cbnote-v9.html:4372-4382` + `:4389`）：

```js
// rsJavaLineComponent：三条分支都返回 Compound（没有返回 TAG_String 的分支）
if(real.length===0)return rsJavaTextComponent({text:''});
if(real.length===1)return rsJavaTextComponent(real[0]);
return[{name:'text',type:NBT_TYPE.String,value:''}, {name:'extra',...}];

// rsJavaBlockNbt：itemType 写死 Compound
{name:'messages',type:NBT_TYPE.List,value:{itemType:NBT_TYPE.Compound, items:[...]}}
```

**当前是合法的**：`itemType` 与每行实际类型一致。实测 `e2e-redstone.nbt` /
`rt.nbt` 的 `messages` 元素类型都是清一色 `compound`（`tmp/sign_audit.js` 验证通过）。

**风险点**：这个一致性靠"调用方恰好只产出 Compound"维持，没有断言保护。
若将来有人给 `rsJavaLineComponent()` 加一个"纯文本行返回 `TAG_String`"的
快路径（很自然的优化），或改成按行内容动态选类型，就会变成混类型列表。
List 的元素类型以声明值为准，混入的 Compound 会被按 String 解析，结果是乱码或空牌。

**若将来要引入 String 行**，必须**整块牌子统一决定 `itemType`**，
不能逐行选类型：

```js
// 4 行全部无样式 → 整块用 TAG_String；只要有一行带样式 → 整块用 TAG_Compound
const plain = lines.every(t => !/[§&]/.test(t));
const itemType = plain ? NBT_TYPE.String : NBT_TYPE.Compound;
```

### 3B.5 两条与兼容性相关的现状记录

1. **`is_waxed: 1`**（`rsJavaBlockNbt()` :4399）。表示牌子已被 honeycomb 锁定，
   玩家无法编辑。`e2e-redstone.nbt` 与 `rt.nbt` 实测都是 `1`。
   这是设计选择，仅记录；若期望"玩家进世界后还能改字"，才需要改成 `0`。
2. **`§` 的处理在两条链路上不同，不能互相复用**：
   - Java 侧 `rsSignLegacyToSegments()` 把 `§d` 这类旧式代码解析成
     结构化 Compound（`color:"light_purple"` 等），这是 1.20 新格式的正确做法。
   - 基岩版侧 `rsSignTextToBedrockLines()` 只按 `\n` 切 4 行、**不剥 `§`**，
     因为基岩版的 `front_text` 直接吃 `§` 字符串（见 `mcwSignBlockEntityTags`）。
   
   两者需求方向相反，改的时候别顺手统一。

## 4. 方向语义：唯一必须背下来的对照表

> ⚠ **绝对不要凭记忆重推这张表**。所有方向错误都来源于"想当然"。
> 下面每一行都有来源，改动必须引用来源。

有**两种互不相容**的语义，混用必错：

- **A. 「朝向」**：值从支撑块**指向**方块本身。
- **B. 「附着面」**：值**就是**支撑块所在的那一侧。A 与 B 互为反面。

### 4.1 逐方块对照

| 方块 | legacy `data` | 基岩版状态 | 语义 | 处理 |
|---|---|---|---|---|
| 红石粉 55 | 0 或 15 | `redstone_signal` 0..15 | data 就是信号强度 | **透传** `data & 0xf` |
| 红石火把 75/76/69 | 1..5 | `torch_facing_direction` (字符串) | legacy=A，基岩=B | **取反**：见 4.2 |
| 中继器 93/94 | `delay*4+dir` | `cardinal_direction` + `repeater_delay` | 都是"朝向" | dir 查表，delay = `(data>>2)&3` |
| 按钮 77 | 低3位 0..5 | `facing_direction` 0..5 | 都是"朝向" | **透传** `data & 7` |
| 梯子 65 | 低3位 2..5 | `facing_direction` 2..5 | 都是"朝向" | **透传** |
| 墙牌 68 | 低3位 2..5 | `facing_direction` 2..5 | 都是"朝向" | **透传** |
| 站立牌 63 | 0..15 | `ground_sign_direction` | — | 透传 |
| 箱子 54 | 低3位 2..5 | `facing_direction` 2..5 | 都是"朝向" | **透传** |
| 音符盒 25 | — | 无状态 | 音高在方块实体 | 见第 3 节 |
| 铁轨 66 / 27 | 低3位 | `rail_direction` | — | 透传 |

### 4.2 火把为什么要取反

```js
// bedrock.js
const BEDROCK_TORCH_ATTACH = ['west', 'east', 'north', 'south', 'top'];  // 下标 = data-1
```

推演：

| data | legacy 含义（A：朝向） | 支撑块在哪 | 基岩版（B：附着面） |
|---|---|---|---|
| 1 | 朝东 | **西**侧 | `west` |
| 2 | 朝西 | **东**侧 | `east` |
| 3 | 朝南 | **北**侧 | `north` |
| 4 | 朝北 | **南**侧 | `south` |
| 5 | 站立 | 下方 | `top` |

来源：[Torch/BS](https://minecraft.wiki/w/Torch/BS) —— *"The face of the block that the torch is attached to"*（值表示火把附着在哪个面的方块上）。

### 4.3 梯子/牌/按钮为什么**不**取反

来源：[Ladder/BS](https://minecraft.wiki/w/Ladder/BS) —— *"The direction from the block the ladder is attached to, to the ladder"*（值是从支撑块**指向**梯子的方向，即"朝向"）。
[Button/BS](https://minecraft.wiki/w/Button/BS)：2=北 3=南 4=西 5=东。
墙牌（中文 wiki）：*"一个依附着它西边方块的告示牌，其朝向的方向为东边"*。

所以这四个的 legacy `data` 与基岩版 `facing_direction` **同义，直接透传**。

### 4.4 几何兜底：`bedrockSupportProbe` / `bedrockFixAttach`

光把映射写对还不够 —— **NBS 的布局本身会把方块放在没有支撑的位置**。

实例（经典布局 `schematic.js:936`）：

```js
blockOther(3, wid - 3, hei - 1, 77, 1);     // 按钮，data=1 要求【下方】有方块
blockOther(3, wid - 2, hei - 1, 35, 11);    // 蓝羊毛 —— 真正的支撑在按钮的【西】侧
```

按钮下方是空气。照 data 原样写，进游戏立刻掉落/悬空。

因此机制如下：

```js
let bedrockSupportProbe = null;   // (x,y,z) => bool，由导出遍历时设置
let bedrockProbeAt = null;        // 当前正在翻译的坐标

function bedrockFacingToSupportOffset(fd)   // 语义A：值→支撑块偏移（取反）
function bedrockAttachOffset(fd)            // 语义B：值→支撑块偏移（同向）
function bedrockFixAttach(fd, isAttach)     // 数据给的面没支撑 → 换一个有支撑的
```

- `bedrockFixAttach(fd, true)` 用于**火把**（值是附着面）。
- `bedrockFixAttach(fd, false)` 用于**按钮 / 梯子 / 墙牌**（值是朝向，支撑在反面）。
- 兜底顺序：数据给的方向 → 四个水平方向 → 上/下 → 都没有则保持原值。
- **必须在 `finally` 里还原** `bedrockSupportProbe` / `bedrockProbeAt`，否则污染后续导出。
- 没有设置 probe 时（纯函数调用 / 单测），行为与原来完全一致。

## 5. 时长：预览图上的时间

## 7. `bedrockPrepareLayout()`：借用布局的标准姿势

这是所有基岩版导出必须先调的函数。它把"借用 NBS 布局"这件事做成原子的，**改了必还原**：

```js
function bedrockPrepareLayout() {
  ensureSchematicState();
  const saveLayout = S.sch_exp_layout;
  const saveTempoReady = S.sch_exp_tempo_ready;
  const saveSink = S.schExpNoteSink;
  const saveSilent = S.schExpSilent;
  try {
    S.sch_exp_layout = 2;            // 强制经典布局
    S.sch_exp_tempo_ready = 0;       // 让 calculateSize 按当前 tempo 重算
    calculateSize();
    S.schExpNoteSink = (nb) => { captured = nb; };
    S.schExpSilent = 1;              // 只要布局，不要落地文件
    schematicExport();
    // ... 收集 SCH_BLOCK/SCH_DATA → cells
  } finally {
    S.sch_exp_layout = saveLayout;
    S.sch_exp_tempo_ready = saveTempoReady;
    S.schExpNoteSink = saveSink;
    S.schExpSilent = saveSilent;
  }
  return { len, wid, hei, cells, noteMap, unmapped, total };
}
```

要点：

- **`S.schExpSilent = 1` 是必须的**。否则 `schematicWriteNbt()` 结尾会额外下载一个 `.schematic`，用户点"导出为基岩版结构"会莫名多收一个文件。
- **布局强制为 2（经典）**。布局 0/1 会引入矿车轨道/梯子/箱子，这些在基岩版朝向差异大，而红石音乐本身不需要。这是导出目标的取舍，不是改布线逻辑。
- `cells` 的键是 `"x,y,z"`（**结构坐标，已镜像**），值是 `{id, data}`。
- `noteMap` 的键同为结构坐标，值为音高 0..24。

## 8. 常见坑（按踩坑频率排序）

1. **不调 `calculateSize()` → 导出空壳，而且不报错**。`len` 会算成 6，一个音符盒都放不下。
2. **忘记 `wid-1-b` 镜像** → 音符盒和它下方的乐器底座错位一格 → 音色全错。
3. **以为世界被镜像，把方向也对调** → 火把/梯子全贴到空气上掉落。`wid-1-b` 只是坐标约定差。
4. **火把按"同义"透传**（漏了取反）→ 火把贴到红石线上掉落。
5. **把 `data` 值当数组下标用**。曾经写过 `[2,3,4,5][data & 3]`（data=2 会取到 4，正北变正西）。正确写法是：取值域就是 2..5 时**直接透传**。
6. **音高写进方块状态而不是方块实体** → 基岩版全部同音高。
7. **`tagList` 参数顺序搞反**：本项目是 `(name, len, type)`。
8. **`Blocks`/`Data` 遍历顺序**：`c` → `a` → `b` 递减，一个字母都不能改。
9. **`S.schExpSilent` 忘了设** → 用户多收一个 `.schematic`。
10. **`bedrockSupportProbe` 忘了在 `finally` 还原** → 污染后续导出。
11. **`base` 变量未定义**（见 9.1）→ 严格模式直接抛 `ReferenceError`。

## 9. 已知问题与历史修复

### 9.1 已修：`.schematic` 导出必然崩溃（本轮发现）

```js
// 修复前 schematic.js:1444
if (!S.schExpSilent) downloadBytes(gz, base);   // base 从未定义！

// schematic.js —— 扩展名按 GML schematic_export.gml:5-6 分两种
let base;
if (structure) {
  // 1.13+ 结构方块：小写 + 空格换下划线 + ".nbt"
  base = String(S.filename || S.song_name || 'song')
    .toLowerCase().replace(/ /g, '_').replace(/\.[^.]*$/, '') + '.nbt';

    .replace(/\.[^.]+$/, '') + '.schematic';

```

- **布局强制经典（2）**：见 7。
- **基岩版红石粉不模拟强度**：NBS 只写 `data` 0/15，基岩版加载后会自己重算。**不要**擅自把 `data=15` 换成 `redstone_block` —— 那会把薄线变成实心方块，几何和充能方式都变了。
- **M2 的 `size` 硬编码 32**：GML 原版就是 `[32, hei, min(len,32)]`（`schematic_export.gml:722-725`），照抄。结构方块单个最大 32×32×32，超出部分需分块，NBS 本身没做。
- **告示牌文字用 1.13 旧式 `Text1`~`Text4`**：**不需要改**。`DataVersion=1519` 会让 DataFixerUpper 正常升级，这是"一次写入、向上兼容"的策略。详见 §3B。

### 9.5 与 cbnote 的策略差异（不在本仓库，均非缺陷）

| 差异 | 位置 | 说明 |
|---|---|---|
| 告示牌文字：旧格式 vs 新格式 | nbsweb `schematicWriteNbt()` / cbnote `rsJavaBlockNbt()` | nbsweb 用 1.13 字段 + `DataVersion=1519`，靠 DFU 升级；cbnote 用 1.20 字段 + `DataVersion=4325` 直写。两种策略各自自洽，见 §3B |
| `messages` 列表元素类型须一致 | `cbnote-v9.html` `rsJavaLineComponent()` (4372) + `rsJavaBlockNbt()` (4389) | 当前产物合法（清一色 Compound）。这是 NBT List 规范的固有约束，改代码时守住即可，见 §3B.4 |
| `is_waxed:1` 锁定牌子编辑 | `rsJavaBlockNbt()` (4399) | 设计选择，仅记录，见 §3B.5 |

### 10.4 写新测试时的注意事项

- `addBlock(x, y, ins, key, vel, pan, pit)` —— **第 3 个参数是乐器编号，不是层号**（层是 `y`）。传错会导致"音符数不对"的假 bug。
- `downloadBytes` 在 `chrome-headless-shell` 里**不会真的落地文件**。要验证"导出了什么"，改为拦截 `downloadBytes` 或直接调导出函数拿返回值。
- 菜单点击要等 ≥600ms：`openReady = (M.ani >= 1)`，第一帧的点击会被忽略。
- `messageDialog` 会把内容推进 `UI.msgQueue` → `UI.modal`，**模态没清掉时后续菜单点击无效**。连续操作前先清 `UI.modal` / `UI.msgQueue`。
- `bedrockPrepareLayout()` 内部会覆盖 `S.schExpNoteSink`，外部设置的 sink 会被冲掉。要抓原始 `noteblocks` 就自己照它的参数跑一遍 `schematicExport()`。
- `window.__NBS__` 暴露了 `G, INS, S, UI, addBlock, gExists, selectionAdd, recalcSong, buildNBS, buildPattern, importMidi`；裸全局也能用（`S`、`UI`、`bedrockBlockFromId` 等）。
